# AI AGENT IMPLEMENTATION GUIDE

## Event-Driven Microservices Streaming Platform

You are a senior software architect and principal Java/Spring engineer.

Your task is to design and implement a production-style, Netflix-inspired video streaming platform as a portfolio-grade distributed system.

The objective is NOT to build a superficial "Netflix clone" with CRUD endpoints.

The objective is to demonstrate strong engineering ability in:

* Java
* Spring Boot
* Spring Security
* Microservices architecture
* Domain-driven service boundaries
* Event-driven architecture
* Apache Kafka
* PostgreSQL
* Redis
* API Gateway
* Authentication and authorization
* Subscription/entitlement systems
* Device management
* Profile management
* Playback state synchronization
* Media processing
* HLS streaming
* Search
* Recommendations
* Trending algorithms
* Analytics
* Financial systems
* Support systems
* Observability
* Resilience
* Testing
* Docker
* CI/CD
* AWS-ready architecture

The system should be designed so that it could eventually be deployed to AWS, but local development must be possible using Docker Compose.

Do NOT attempt to implement everything at once.

Work incrementally.

# 2. IMPORTANT ARCHITECTURAL PRINCIPLES

Follow these principles throughout implementation.

## 2.1 Do not create microservices simply because microservices sound impressive

Every service must have a clear responsibility and bounded context.

Avoid:

* shared databases
* random service-to-service calls
* duplicated business logic
* services that only wrap CRUD tables
* excessive synchronous communication

Prefer:

* clear ownership
* asynchronous events where appropriate
* REST for synchronous queries/commands
* Kafka for domain/integration events
* eventual consistency where appropriate

# 6. PHONE VERIFICATION

Phone verification is intentionally SIMULATED for the initial system.

Do NOT integrate Twilio or another SMS provider yet.

However, design the system so a real provider can be added later without changing business logic.

Create an abstraction similar to:

```text
SmsProvider
    |
    +-- MockSmsProvider
    |
    +-- TwilioSmsProvider (future)
```

The mock provider should:

* generate/send simulated OTPs
* log the OTP during development
* expose the OTP through a development-only mechanism if useful
* never expose OTPs in production

OTP requirements:

* 6 digits
* expiration, e.g. 5 minutes
* limited verification attempts
* resend cooldown
* resend limits
* invalidate after successful verification
* only one active OTP per phone
* hashed OTP storage
* rate limiting

Example conceptual flow:

```text
User
 |
 | phone number
 v
Auth Service
 |
 | generate OTP
 v
Verification subsystem
 |
 v
Mock SMS Provider
 |
 v
Development console/UI
```

Create the abstraction now so replacing the provider later is straightforward.

```text

max_concurrent_streams

max_resolution
hdr_enabled

audio_quality

downloads_enabled
max_download_devices

offline_viewing

kids_profiles_enabled
```

Example:

```text
Mobile
KSh 299/month

max_profiles = 1
max_registered_devices = 3
max_concurrent_streams = 1
max_resolution = 720P
downloads_enabled = true
```

Another:

```text
Standard

max_profiles = 3
```

Another:

```text

```

# 10. ENTITLEMENTS

Separate the concept of:

```text
Plan
Subscription
Entitlement
```

A subscription references a plan/version.

The effective capabilities of the subscription should be represented as entitlements.

Example:

```json
{
  "maxProfiles": 5,
  "maxRegisteredDevices": 6,
  "maxConcurrentStreams": 4,
  "maxResolution": "4K",
  "downloadsEnabled": true,
  "maxDownloadDevices": 4,
  "hdrEnabled": true
}
```

Playback and other services should ask:

```text
Does this subscription have entitlement X?
```

rather than:

```text
if plan == PREMIUM
```

This is a critical architectural requirement.

```text

4K
```

Support:

* plan versions
* effective dates
* active/inactive status
* future plan versions
* optional migration rules

# 18. PROGRESS EVENTS

Do not write playback progress to PostgreSQL every second.

Use an event-driven approach.

Player can periodically emit progress:

```json
{
  "eventType": "PLAYBACK_PROGRESS",
  "eventId": "...",
  "profileId": "...",
  "accountId": "...",
  "deviceId": "...",
  "contentId": "...",
  "positionSeconds": 2832,
  "durationSeconds": 6740,
  "timestamp": "..."
}
```

Use Kafka and/or Redis to handle high-frequency state.

Persist durable watch state asynchronously.

Implement idempotency.

Consider:

* event ordering
* duplicate events
* stale events
* concurrent devices
* optimistic concurrency
* last-write semantics
* version numbers

Do not blindly overwrite newer progress with an older event.

# 20. TRENDING

Build a real trending system.

Trending is NOT simply:

```sql
ORDER BY lifetime_views DESC
```

Trending should measure recent momentum.

Potential scoring model:

```text
TrendingScore =
    recent views
  + completions
  + likes
  + watchlist additions
  + weighted velocity
  - time decay
```

For example:

```text
5 × views_last_1h
3 × views_last_6h
2 × completions_last_24h
1 × likes_last_24h
- decay
```

The exact algorithm can evolve.

Use Kafka events as input.

Potential architecture:

```text
Playback
   |
   v
Kafka
   |
   v
Trending Consumer
   |
   +-- Redis counters
   |
   +-- ranking computation
   |
   v
Trending results
```

Support regional trending where possible.

For example:

```text
Global Trending
Kenya Trending
East Africa Trending
```

# 42. DATA OWNERSHIP

Each service should own its database/schema.

Avoid:

```text
All services
     |
     v
One giant PostgreSQL database
```

Prefer:

```text
Auth -------- auth DB
User -------- user DB
Catalog ----- catalog DB
Subscription  subscription DB
Billing ------ billing DB
Watch History  watch-history DB
```

Local development may use one PostgreSQL server with separate databases/schemas if necessary, but logical ownership must remain clear.

A service must not directly query another service's tables.

# 47. IDEMPOTENCY

Implement idempotency where duplicate requests/events could cause damage.

Important examples:

```text
Payment processing
Subscription creation
Refunds
Kafka consumers
Watch progress
Notification dispatch
```

For example, a duplicate:

```text
PAYMENT_COMPLETED
```

must not activate the subscription twice or create duplicate financial records.

# 63. WHAT NOT TO DO

Do NOT:

* hard-code subscription plans
* hard-code device limits
* hard-code profile limits
* store OTPs plaintext
* store passwords plaintext
* let services directly query another service's DB
* send every playback second to PostgreSQL
* make playback synchronously depend on analytics
* make playback synchronously depend on trending
* create Kafka topics for meaningless events
* create 20 microservices on day one
* introduce Kubernetes before the application works
* build complex ML before collecting useful events
* expose permanent video URLs
* put secrets in Git
* ignore idempotency
* ignore event ordering
* ignore observability
* build an admin UI with a single ADMIN role
* silently change existing subscription terms by mutating plans

---

# 64. ENGINEERING STYLE

Code should be:

* readable
* idiomatic Java
* strongly typed
* properly layered
* testable
* documented where reasoning matters

Prefer:

```text
Controller
    ↓
Application Service
    ↓
Domain Logic
    ↓
Repository
```

Do not create unnecessary abstractions.

Avoid giant service classes.

Avoid anemic "everything is a DTO" architecture.

Use domain concepts where they genuinely improve correctness.
